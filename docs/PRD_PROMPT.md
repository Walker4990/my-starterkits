# PRD 작성 메타 프롬프트: 견적서 웹 뷰어 MVP

> 사용법: 아래 `---` 이후의 내용을 새 Claude Code 세션에 그대로 붙여넣는다. 결과물은 `docs/PRD.md`로 생성된다. 서브에이전트 `notion-api-expert`를 쓰므로 에이전트 파일이 등록된 **새 세션**에서 실행한다.

---

# 역할

당신은 10년 차 시니어 프로덕트 매니저 겸 풀스택 아키텍트입니다.
1인 개발자가 2주 안에 출시할 수 있는 **MVP PRD**를 작성합니다. 범위를 넓히기보다 줄이는 쪽으로 판단하세요.

# 목표

`docs/PRD.md` 파일 **하나**를 한국어로 작성하세요. 코드는 작성하지 않습니다. PRD만 작성합니다.

# 제품 개요

- 관리자(1인 개발자/프리랜서)가 **Notion 데이터베이스**에 견적서 내용을 입력한다.
- 클라이언트는 전달받은 **고유 공유 링크**로 접속해 견적서를 **웹에서 확인**한다.
- 클라이언트는 같은 화면에서 견적서를 **PDF로 다운로드**한다.
- Notion이 유일한 데이터 입력 창구(Source of Truth)이며, 별도 관리자 화면은 만들지 않는다.

# 이미 확정된 결정 (재논의 금지)

| 항목 | 결정 |
|------|------|
| 데이터 입력 | Notion 데이터베이스 (Notion API 연동) |
| 클라이언트 접근 | 견적서별 추측 불가능한 토큰이 포함된 공유 링크. 로그인 없음 |
| 프레임워크 | 기존 프로젝트의 Next.js App Router (버전은 `package.json` 기준) |
| 구조 | 레이어드: Page/Component → hooks → services → repositories → Notion client |

# 먼저 할 일 (PRD 작성 전)

1. 루트 `CLAUDE.md`와 `~/.claude/CLAUDE.md`를 읽고 아키텍처·원칙·완료 조건을 파악한다.
2. `package.json`, `app/`, `services/`, `repositories/`, `types/`, `lib/` 구조를 훑어 **재사용할 수 있는 것**(예: `lib/api/client.ts`의 `X-Request-ID`, `types/common.ts`의 `ApiResponse`, `ApiError`, 기존 UI 컴포넌트)을 정리한다.
3. Notion 연동 부분(6절 데이터 모델, 9절 캐싱·rate limit·재시도, 10절 아키텍처, 11절 타입 설계)은 **`notion-api-expert` 서브에이전트에 위임**한다. (아래 "서브에이전트 활용" 참고)
   PDF 생성 방식은 Context7 MCP로 **최신 문서를 확인**한 뒤 근거로 삼는다.
4. 기존 스타터킷의 Supabase/FastAPI가 이 MVP에 필요한지 판단하고, 불필요하면 PRD에서 **제외 범위**로 명시한다.
5. 정보가 부족해 PRD의 품질이 떨어질 것 같으면 **작성 전에 질문**한다. 추측으로 채우지 않는다. 질문은 한 번에 최대 4개로 묶는다.

# 서브에이전트 활용

`.claude/agents/notion-api-expert.md`(Notion API 전문가, 읽기 전용, `model: sonnet`)를 Agent 도구로 호출한다. 에이전트가 목록에 없으면 세션을 재시작하거나 `general-purpose`(sonnet)에 해당 파일을 읽게 한 뒤 같은 지침으로 실행한다.

1. 호출 전에 `docs/NOTION_API_GUIDE.md`가 있으면 먼저 읽고, 이미 검증된 내용은 다시 조사시키지 않는다. 가이드에서 "확인 필요"로 남은 항목만 에이전트에게 추가 확인을 요청한다.
2. 에이전트에게 맡길 질문
   - 견적서·품목 데이터 소스의 속성 구성과 Relation 조회 방식(품목 역방향 필터 1회 쿼리, relation 25건 초과 시 잘림 주의)
   - 공유 토큰 필터, 중복 토큰 처리, 페이지네이션
   - rate limit(플랜별 수치), 429/529/5xx/타임아웃 재시도 책임 분담
   - Notion raw 타입 → 도메인 타입 변환 위치와 `NOTION_SCHEMA_MISMATCH` 처리
3. 에이전트 결과는 **근거로만 사용**하고, PRD는 직접 작성한다. 에이전트가 "확인 필요"로 표시한 내용은 PRD에도 "확인 필요"로 남긴다.
4. 반드시 반영할 확인된 사실
   - SDK는 429/529를 내장 재시도하지만 `dataSources.query`(POST)의 5xx와 타임아웃은 재시도하지 않는다. 따라서 `lib/notion`의 재시도 범위를 이에 맞게 정의한다.
   - SDK 기본 `timeoutMs`는 60초다. PDF 5초 목표와 충돌하므로 타임아웃·최대 대기 시간 설정을 요구사항에 포함한다.
   - rate limit은 Business/Enterprise 600회, 그 외 180회 (60초 창). "평균 초당 3회"는 비-Business 기준임을 명시한다.
   - 품목·견적서 두 데이터베이스 모두 Integration에 공유해야 한다. 미공유 시 404.

# 기존 문서 처리

- `docs/PRD.md`가 이미 있으면 **덮어쓰기 전에 내용을 읽고**, 변경이 필요한 부분만 수정해 문서 버전을 올린다(예: v0.1 → v0.2). 변경 요약을 문서 첫머리 표에 한 줄로 남긴다.
- 사용자가 확정한 결정과 오픈 이슈 선택 결과가 있으면 보존한다.

# PRD 필수 목차

각 섹션을 빠짐없이, 아래 순서로 작성하세요.

1. **배경과 문제 정의** — 현재 견적서 전달 방식의 불편과 이 제품이 해결하는 것
2. **목표 / 비목표** — 성공 지표(측정 가능한 수치 포함)와 이번 MVP에서 하지 않는 것(관리자 UI, 결제, 전자서명, 견적 수정 요청, 다국어 등)
3. **사용자 페르소나** — 관리자, 클라이언트
4. **사용자 스토리** — `~로서 ~하고 싶다, 그래서 ~` 형식, P0/P1 우선순위 표기
5. **기능 요구사항** — 기능별 ID(`FR-01`…), 우선순위, **인수 기준(Given/When/Then)**
6. **Notion 데이터 모델** — 데이터베이스 속성 표(속성명, Notion 타입, 필수 여부, 설명). 최소 견적번호, 클라이언트명, 발행일, 유효기간, 품목(품명·수량·단가), 세율, 비고, 상태, 공유 토큰을 검토한다. 품목을 하위 데이터베이스로 둘지 한 행으로 둘지 **비교 후 하나를 추천**한다.
7. **화면 및 라우트 설계** — 라우트 표(예: `/quotes/[token]`), 화면별 구성 요소, 로딩/빈 상태/에러/만료/존재하지 않는 링크 상태
8. **PDF 요구사항** — A4 레이아웃, 한글 폰트 처리, 웹 화면과 PDF의 일관성, 파일명 규칙. 구현 방식(`@react-pdf/renderer` / Puppeteer 등 서버 렌더링 / 브라우저 인쇄 CSS)을 **장단점·배포 환경 제약·번들 크기로 비교하고 하나를 추천**한다. 새 라이브러리는 **제안일 뿐 도입 확정이 아니며** 사용자 확인이 필요함을 명시한다.
9. **비기능 요구사항** — 보안(토큰 길이·추측 불가, Notion API 키 서버 전용, 링크 만료/폐기), 성능(캐싱/ISR/revalidate 전략과 Notion rate limit 대응), 접근성, 반응형(모바일 열람), 모든 요청의 `requestId` 추적, 에러를 삼키지 않는 처리 방침
10. **시스템 아키텍처** — 데이터 흐름도(텍스트 다이어그램), 계층별 책임, 디렉토리 배치안, 환경변수 목록
11. **타입 설계** — Notion raw 타입(`Notion*`)과 도메인 타입의 분리 및 변환 위치(repository 계층). `any` 없이 설계한다.
12. **테스트 전략** — TDD 순서, 계층별 테스트 범위(services 위주, repository는 mock), 핵심 테스트 케이스 목록
13. **마일스톤** — 1인 개발 기준 단계별 작업과 예상 일정. 각 단계는 독립적으로 동작 확인이 가능해야 한다.
14. **리스크와 대응** — Notion API 제한/장애, 한글 PDF 폰트, 링크 유출, 서버리스 환경의 PDF 생성 한계 등
15. **오픈 이슈** — 사용자의 결정이 필요한 항목 목록(선택지와 추천안 포함)

# 제약

- `any` 금지, 과도한 추상화 금지. 단순함, 일관성, 유지보수성 우선.
- 새 라이브러리 도입이나 큰 변경은 **제안으로만** 쓴다. 확정 표현을 쓰지 않는다.
- MVP 범위를 엄수한다. 있으면 좋은 기능은 모두 "비목표" 또는 "P1(후속)"로 분류한다.
- 모든 기능의 인수 기준에 아래 완료 조건을 공통 항목으로 포함한다.
  - `npm run test`, `npx tsc --noEmit`, `npm run lint` 모두 통과
- 근거 없는 수치나 외부 사실을 만들어내지 않는다. 확인하지 못한 내용은 "확인 필요"로 표시한다.

- 한국어 마크다운, 제목 계층은 `#` → `##` → `###`까지만 사용

- 다이어그램은 코드 블록 안의 텍스트로 작성
- 문서 첫머리에 문서 버전, 작성일, 상태(Draft)를 둔다
- 문서 마지막에 "사용자 확인이 필요한 항목" 체크리스트를 둔다
